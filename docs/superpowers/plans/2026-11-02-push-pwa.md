# Notifications Web Push dans la PWA — Plan d’implémentation

> **Pour les agents d’exécution :** appliquer ce plan étape par étape avec des tâches cochables et des vérifications indépendantes.

**Objectif :** permettre à un utilisateur connecté d’activer ou désactiver volontairement les notifications push et recevoir des alertes génériques pour les événements qui alimentent déjà les notifications Madclothes.

**Architecture :** le navigateur demande l’autorisation après le clic de l’utilisateur, crée une souscription Push via le service worker et l’enregistre dans une nouvelle table Neon par une API authentifiée. Le serveur Node utilise VAPID et `web-push` pour avertir le destinataire après la validation des événements métier; les erreurs de push n’annulent jamais une demande, un message ou un avis déjà enregistré. Le service worker affiche et ouvre les notifications sans inclure de contenu privé.

**Technologies :** Vite 5, `vite-plugin-pwa`/Workbox, React 18, TypeScript, Vercel Node Functions, Neon PostgreSQL, `web-push`, Vitest.

**Spécification :** demande de l’utilisateur dans la conversation du 2 novembre 2026 : « Bien je veux que ma pwa puisse avoir l'autorisations d'activer […] et aussi d'envoyer des notifications push ».

## Structure du projet concernée

- `src/pages/Account.tsx` : commande d’activation/désactivation dans la section Notifications existante.
- `src/lib/push-notifications.ts` : support navigateur, conversion de clé VAPID et gestion de souscription.
- `public/push-handler.js` et `vite.config.ts` : événements `push`/`notificationclick` ajoutés au service worker Workbox existant.
- `server/api.ts` et `server/push.ts` : API authentifiée, validation, envoi VAPID et purge des souscriptions expirées.
- `db/migrations/0003_push_subscriptions.sql` : stockage privé des endpoints et clés de souscription.
- `.env.example` et `docs/deployment.md` : configuration locale et consignes de déploiement.
- `src/test/` : tests d’API et d’interface sans accès à la base réelle ni aux services push externes.

## Contraintes globales

- Demander la permission uniquement à la suite du clic « Activer les notifications »; ne pas solliciter l’utilisateur au démarrage.
- Ne jamais exposer `VAPID_PRIVATE_KEY` via `VITE_`, le bundle client, les réponses HTTP ou les journaux. Seule `VITE_VAPID_PUBLIC_KEY` est publique; le serveur utilise `VAPID_PRIVATE_KEY` et `VAPID_SUBJECT`.
- Exiger l’authentification, l’état de compte actif, la validation des champs et l’appartenance du profil courant pour créer/supprimer ses souscriptions.
- Valider les endpoints HTTPS contre les domaines des services push connus (FCM, Apple Web Push, Mozilla Autopush, Windows Push); refuser IP, loopback, ports non standards, credentials, URL malformée ou hôte non autorisé afin de prévenir SSRF.
- Borner endpoint (2 048 caractères), clés, nombre de souscriptions actives par profil (10), et taille du payload. Ne jamais journaliser endpoint, clés, message privé ou corps de push.
- Envoyer des textes génériques sans le contenu d’un message : nouveaux messages, demande de commande, changement d’état, nouvel avis. Les liens de clic sont des chemins internes sûrs, jamais une URL arbitraire.
- Après un échec d’envoi, préserver la transaction métier; supprimer une souscription uniquement pour les réponses push définitives 404/410.
- Ne pas lire ni modifier `.env.local`. Ne pas exécuter la migration sur la base Neon partagée, ne pas envoyer de push externe pendant les tests.
- Travail local seulement : aucun `git add`, commit, push, déploiement ou changement distant.

## Points de revue et tests associés

- Utilisateur non connecté/inactif : aucune souscription n’est enregistrée; l’API renvoie une erreur d’authentification/autorisation.
- Endpoint localhost, IP privée, domaine similaire mais non autorisé, HTTP, URL avec identifiants ou port atypique : rejet avant tout appel à `web-push`.
- Plus de 10 souscriptions ou clés/endpoints invalides : rejet avec réponse contrôlée, sans journalisation de la valeur.
- Permission refusée, navigateur sans Push API/service worker, clé publique absente : expliquer l’état et ne pas laisser croire que les alertes sont actives.
- Erreur réseau ou erreur fournisseur après une transaction métier : succès métier conservé; une réponse 404/410 supprime seulement la souscription expirée.
- Clic sur une notification : ouvrir une route Madclothes connue sur la même origine; une URL malveillante tombe sur `/compte`.

## Reprise frontend — 2026-11-06

Le backend Push et les routes d’abonnement n’ont pas été modifiés. Le frontend comprend désormais un réglage accessible dans le compte, un client navigateur qui demande la permission uniquement après clic, valide la clé publique VAPID avant de solliciter l’utilisateur, enregistre/retire l’abonnement via l’API existante et nettoie une nouvelle souscription locale si son enregistrement serveur échoue. Le service worker affiche des alertes génériques, borne leur texte et ne permet d’ouvrir que des routes Madclothes internes autorisées. Workbox importe ce gestionnaire; les règles de cache API restent `NetworkOnly`. Le middleware local transmet les variables VAPID serveur au seul processus Node de développement. `.env.example` et la documentation précisent les prérequis, sans contenir de secret réel ni modifier `.env.local`.
